# Security and deployment notes

## Supabase authentication and lead isolation

- Keep `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and `LOVABLE_API_KEY` configured only in their intended runtime environments. Never commit secrets or print key values in logs. The Lovable gateway key must remain server-side.
- Review `supabase/migrations/20261023000100_secure_leads_rls.sql` before applying it to any shared database. It enables RLS on `public.leads`, removes the table's existing policies, and replaces them with policies that match `user_id` to `auth.uid()`. It does not delete lead data, but it changes access behavior for all existing clients of that table.
- This repository does not contain prior migrations defining the complete production schema, and this task did not connect to the remote database. Confirm that the remote `public.leads` table and its `user_id` column match the generated types before applying the migration. Do not apply it directly to production from this PR.
- Run the RLS regression checks against an isolated local Supabase database with `supabase test db` after applying local migrations. The tests use fixed fixture UUIDs and roll back their rows.
- The current import uses the unique conflict target `user_id,source,source_id`. Verify that the deployed schema has a matching unique constraint/index; an import conflict will return an error if that constraint is absent.

## Password recovery redirects

In the Supabase Dashboard, configure the project's **Site URL** and **Redirect URLs** for the exact app origins used in development and deployment. The password recovery redirect generated by this app is:

- `/auth?mode=reset` on the current origin.

Allow the full callback URL for each approved origin (for example `https://your-real-domain.example/auth?mode=reset`) and keep the base app URL configured as the Site URL. Replace the example host with the actual domain; do not allow arbitrary origins. Configure the Supabase email template/provider so recovery links are delivered. The app does not verify external e-mail delivery or provider configuration.

## OpenStreetMap availability and data quality

The import resolves each supported city through Nominatim and checks the administrative relation's name, country, and São Paulo state before using its derived Overpass area. If the city boundary cannot be verified, import stops rather than using a guessed bounding box. Public Nominatim/Overpass services may rate-limit or be unavailable; failures are surfaced and should be retried later. A saturated result limit is reported as incomplete rather than silently treated as a complete dataset.

OpenStreetMap data is public data but may be incomplete or stale. Validate business details and the lawful basis/legitimate-interest assessment before commercial outreach. Preserve manual message approval and honor any internal suppression/no-contact list if one is adopted. This code does not automate sending messages or independently determine LGPD compliance.
